The one thing that decides whether this works

You are learning to direct AI, not to ask it. Someone who can't read code receives AI-generated slop and can't tell. So Block 1 of every single day is AI-as-tutor-only, no generated code. Everything else is AI-on, full throttle.

Day 0 — Setup

Two hours, done before Day 1 starts.

Machine decision

The Windows PC is your daily driver, running WSL2. Fighting an unfamiliar OS for 90 straight days taxes the only thing that actually matters: showing up daily. WSL2 puts a real Ubuntu Linux underneath your Windows desktop, so every command in this plan and in ~95% of tutorials works verbatim, while the windows, shortcuts and file manager stay familiar.

Windows also has the edge for the AI-heavy later weeks: with an NVIDIA GPU you can run local models far faster than a Mac can. Do not install Linux natively.

Step 1 — Turn on WSL2 10 MIN

Open PowerShell as Administrator, run wsl --install, reboot. Then launch the Ubuntu app from the Start menu and set a username and password when prompted.

Right terminal, every time

Everything below is typed in the Ubuntu terminal, not PowerShell. If your prompt starts with PS C:\ you're in the wrong window.

Step 2 — Install your toolchain

sudo apt update && sudo apt upgrade -y
sudo apt install -y python3 python3-pip python3-venv git ripgrep curl unzip

# Node 22+ (Claude Code needs it; Ubuntu's apt version is too old)
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs

# uv — fast Python package manager
curl -LsSf https://astral.sh/uv/install.sh | sh

# Claude Code
npm install -g @anthropic-ai/claude-code

# Identify yourself to Git
git config --global user.name "Your Name"
git config --global user.email "you@email.com"
git config --global init.defaultBranch main
git config --global core.autocrlf false   # keep LF, or every diff looks changed

Step 3 — Install on Windows normally

  • Cursor — cursor.com. Add its WSL extension, then always open projects by typing cursor . from inside the Ubuntu terminal. The window is Windows; everything it runs is Linux.
  • Docker Desktop — docker.com. Then Settings → Resources → WSL Integration → enable your Ubuntu distro.
The one rule that makes WSL2 pleasant

All project files live in the Linux filesystem — ~/dev/ — never in /mnt/c/Users/.... Files on the Windows drive are 10–20× slower to read and cause permission problems. This single mistake is why people think WSL is bad. Get it right and it isn't.

Last Day 0 step — put this plan in a Git repo

Don't leave this file in Downloads. It lives next to your daily log, in version control, from Day 0 — and it's your first real Git exercise. In the Ubuntu terminal (swap WINDOWSNAME for your Windows username; ls /mnt/c/Users/ shows it):

mkdir -p ~/dev/90-day && cd ~/dev/90-day
git init
cp /mnt/c/Users/WINDOWSNAME/Downloads/90-day-plan.html .
touch log.md
git add . && git commit -m "Day 0: plan + log"

Copying out of /mnt/c/ once is fine. Working there daily is not. Now create a new empty repo on github.com called 90-day (no README, no .gitignore) and connect it:

git remote add origin https://github.com/YOURNAME/90-day.git
git push -u origin main

If it asks for a password, GitHub wants a Personal Access Token, not your account password: github.com → Settings → Developer settings → Personal access tokens → Tokens (classic) → Generate new token → tick repo → paste the token as the password. Then run git config --global credential.helper store so you only do this once.

~/dev/ is now where all 90 days of work lives. Every project gets its own folder in there.

Your daily rhythm

Five hours, in this order, every day.

Block 4 is not optional

Every day, in log.md, answer three things:

  1. Three things I learned today — in my own words, no copy-paste
  2. One error I hit, and its actual cause
  3. One line of code AI wrote today that I couldn't explain — and now can

Commit it. On Day 90 this log is your proof you learned something.

On a four-hour day: cut Block 2 to 90 min and Block 3 to 30 min. Never cut Block 1 or Block 4.

Phase 1 · Days 1–30

Foundations

By Day 30 you can write Python unaided, move around a terminal without thinking, and point at one working thing you shipped.

Daily 20-minute drill — starts Week 2, runs forever

Open a repo you didn't write (start with your own from last week, then move to small open-source projects), pick a random function, and explain out loud what every line does. Then have an AI check you. Reading unfamiliar code is the exact skill this whole plan is built on — train it directly, not just as a side effect of writing your own.

DAYS 1–7

Terminal, Git, first Python

  • Block 1 — MIT The Missing Semester of Your CS Education (missing-semester.mit.edu), lectures 1–6, one per day. Do the exercises.
  • Block 2 — Harvard CS50P (cs50.harvard.edu/python), Lectures 0–2 and the core problem set for each. Skip the optional “more comfortable” extras — they polish, they don't teach faster. Type everything.
  • Block 3 — OverTheWire Bandit (overthewire.org/wargames/bandit), levels 0–15. The fastest way to get fluent in the Linux terminal — a puzzle game you'll actually enjoy.
  • Ship Friday — a Python CLI script in a GitHub repo, with a README you wrote yourself.
DAYS 8–14

Python core + how the internet works

  • Blocks 1–2 — CS50P Lectures 3–6 and problem sets: exceptions, libraries, unit tests, file I/O.
  • Block 3 — TryHackMe Pre Security path, complete it. How networking, HTTP and DNS actually work — the plumbing under every app and API you'll build. Cancel the sub after this month.
  • Ship Friday — a script that calls a public API (try https://api.github.com/users/YOURNAME) and saves the result to a file. With tests.
DAYS 15–21

Finish Python, start web security

  • Blocks 1–2 — CS50P Lectures 7–9 and the final project. Get the certificate.
  • Block 3 — how the web really works, hands-on: open your browser's dev tools, watch the network tab as a page loads, then hit a free public API from the command line with curl. Own the words request, response, status code, header, JSON.
  • Ship Friday — CS50P final project on GitHub.
DAYS 22–30

First real app + first API calls

  • Block 1 — read your own Week 1–3 code and refactor it by hand. Uncomfortable, and the point.
  • Block 2 — build a small web app: Python + FastAPI + SQLite. A task tracker or link saver, boring on purpose. Deploy it on Railway so a public URL exists.
  • Block 3 — the basics that make an app real: environment variables and secrets (never hard-code an API key), reading logs, what HTTPS does, and just enough auth to add a login.
  • Also this week — write a Python script that calls the Claude API and the OpenAI API directly, no framework. Understand: API key, messages array, tokens, temperature, max_tokens.
Day 30 checkpoint

You should be able to:

  • Write a 100-line Python program with no AI
  • Explain what a request, a response, a status code and a header are
  • Read an AI-generated function and say what each line does
  • Point at a live URL that is yours
Phase 2 · Days 31–60

Build with AI — the product shapes

By Day 60 you can build the handful of shapes almost every AI product is made of, and you understand what's happening under the hood well enough to debug it and explain it. No niche committed — you're building range.

The disposable-project rule

Everything you build in Phase 2 is a throwaway you'll never sell. That's deliberate — it removes the “is this the right idea?” pressure that pulled you into niche-juggling, and lets you focus purely on the skill. Pick anything low-stakes to practise on; the product decision comes later, from a position of skill.

DAYS 31–37

The web layer + your first AI feature

  • Block 1 — javascript.info parts 1–2 through “Objects”, plus MDN's HTML basics and CSS first steps. Enough to read and shape a frontend; you're not becoming a frontend dev.
  • Block 2 — take your Week 4 app and add one real AI feature (summarise / classify / answer-from-text). Learn Cursor properly: agent mode, @-referencing files, a .cursorrules file stating your stack.
  • Block 3 — prompt engineering, done properly: read Anthropic's and OpenAI's prompting guides, then build a prompt you iterate on with measured before/after, not vibes.
DAYS 38–44

Data + how LLMs actually work

  • Block 1 — SQLBolt (all 18 lessons), then move your app to PostgreSQL. Every real product has a database; this is non-negotiable literacy.
  • Block 2 — learn Claude Code in the terminal for multi-file work; write a CLAUDE.md; practise Git branches and pull requests on your own repo.
  • Block 3 — the fluency block — understand the machine: tokens, embeddings, context windows, temperature, what “training vs inference” means, why models hallucinate, and the difference between a base model, an instruct model and a reasoning model. Enough to explain each out loud.
DAYS 45–51

LLM engineering — the core building blocks

Build each yourself in Python, no frameworks first. These four are what every AI product is assembled from:

  • Tool-use loop — model requests a function, your code runs it, feeds the result back. This is all an “agent” is.
  • Structured output — force valid JSON, parse it, handle failure. The backbone of connecting AI to real software.
  • RAG — chunk a folder of documents, embed, retrieve, answer from them. The single most-requested business feature (“a bot that knows our stuff”).
  • An eval — 20 test cases, a scoring function, two models compared numerically. This is how you make AI reliable instead of a demo.
  • Only after building them raw, try a framework once (LangChain or the OpenAI/Anthropic SDKs' higher-level bits) so you know what it's hiding.
DAYS 52–55

Ship one thing end to end

  • Block 1+2 — combine the Week 7 pieces into one small working product on your disposable idea: a frontend, a database, auth, and an AI feature that does something genuinely useful. Deploy it publicly.
  • Put a real cost meter on it: track tokens and dollars per request. Knowing unit economics is what separates “cool demo” from “business”.
  • Block 3 — one afternoon on voice + multimodal: wire up a speech-to-text → LLM → text-to-speech loop. This is the exact spine of voice-agent products, built once so you know the whole category is within reach.
Day 60 checkpoint
  • You've shipped one full-stack app with a working AI feature, live on the internet
  • You can explain tokens, embeddings, RAG, tool-use and evals to another person, unaided
  • You know what one AI request costs you and why
Phase 3 · Days 61–90

Depth and range — become dangerous with AI

Widen across the product shapes you haven't touched, go one level deeper on how models work, and pressure-test AI by breaking it. End as a generalist who can build most things and explain all of them — with no niche locked in.

DAYS 61–67

Agents that do real work

  • Build a multi-step agent that plans, calls several tools, and recovers from its own mistakes — beyond the single tool-loop from Week 7.
  • Give it real tools: web search, a database, sending an email, calling an external API. This is the “AI does the busywork” pattern businesses pay for — automation, not chat.
  • Learn where agents fall over (loops, runaway cost, wrong tool) and how to put guardrails on them.
DAYS 68–74

One level under the hood

  • Work Andrej Karpathy's “Neural Networks: Zero to Hero” series, at least through building a tiny GPT. You'll never train frontier models — but building one small one end to end is what turns “I use LLMs” into “I understand LLMs”.
  • Learn fine-tuning vs RAG vs prompting — what each is for, what each costs, when a business actually needs which. This is the question you'll be asked most, so own the answer.
  • Run one small open model locally (Ollama). Understand the privacy/cost trade-off vs an API — the deciding factor for a lot of business use.
DAYS 75–81

Break AI to understand it

One week of red-teaming — the fastest route to understanding how models really behave, and it's the part you were most drawn to. Legal targets only.

  • Prompt injection, jailbreaks, system-prompt leaking, tool abuse. Practise on public CTFs: Gandalf (Lakera) and HackAPrompt.
  • Attack your own Phase 2 app: make it ignore instructions, leak its prompt, or misuse a tool. Then fix each hole — now you can build AI products that don't fall over in public.
  • Read about indirect prompt injection (malicious instructions hidden in data an AI reads). The live frontier, and knowing it makes you the person in the room who understands why agents are risky.
DAYS 82–90

Consolidate + point at money

  • Build one portfolio-grade thing that shows range: pick your best Phase 2–3 project and make it genuinely good — polished, deployed, documented.
  • Write three public posts explaining something you now understand deeply (RAG, agents, what fine-tuning is really for). Teaching is how you prove fluency and how an audience/clients find you.
  • Do a money map, not a commitment: list 5 ways your new skills convert to income (freelance AI automation, small SaaS, “add AI to X” for local businesses, consulting, content). Rank by what you'd actually enjoy. You now choose from skill, not from guessing.
  • Re-read log.md from Day 1, then write your own next 90-day plan.

Which model for which task

Route by task, not loyalty. Product names churn every few months — re-check this table quarterly.

TaskUseWhy
Multi-file changes, refactors, whole-repo workClaude (Claude Code / Cursor)Leads coding benchmarks; strongest on long-context codebase work
Long-form writing; explaining your own code back to youClaudeBest prose, least filler
Second opinion on a hard bugChatGPTDifferent failure modes catch what the first model missed

Weekly habit

Run one identical real task through two models and keep the better answer. That habit beats every comparison article, including this table.

Fluency habit

Don't get loyal to one model — loyalty is the opposite of fluency. The person who knows which model wins which task, and can say why, is the one who looks like an expert. Re-run the two-model test weekly; the table above will drift within months.

The eight rules that make or break this

  1. Never paste code you can't explain. Ask “explain line 7” until you can. Then delete it and retype from memory.
  2. You write the tests. AI writes the function, you write the test. That reverses the trust relationship correctly.
  3. Ask for three approaches, then choose. “Give me 3 ways to do this with trade-offs” produces learning; “do this” produces dependence.
  4. Commit every day. A green GitHub graph is the cheapest credibility you will ever buy.
  5. Stuck more than 20 minutes? Paste the exact error, your code, and what you already tried. Never “it doesn't work”.
  6. One project at a time. Depth beats a graveyard of half-built repos.
  7. One project per machine per day. Push before you close the laptop, pull before you start.
  8. Never run LLM-generated commands against anything you care about without reading them first. rm -rf looks the same in every language.
The legal line — no exceptions

The Week 11 red-teaming happens on public CTFs built for it (Gandalf, HackAPrompt) and on your own app. Never point these techniques at someone else's live product without a published bug-bounty invitation — “just to see” is the line between research and an offence.

What Day 90 looks like

  • Write Python confidently and read most code AI hands you
  • Built all the core AI product shapes yourself: tool-use, structured output, RAG, evals, a multi-step agent, and a voice loop
  • Shipped a full-stack app with a working AI feature, live and cost-metered
  • Can explain how LLMs work — tokens, embeddings, training vs inference, fine-tuning vs RAG — to anyone
  • Built one tiny model from scratch, so the black box isn't a black box
  • Red-teamed AI on legal targets and hardened your own app against it
  • One polished portfolio project, three public write-ups, 90 days of commits
  • A ranked money-map — five ways to earn from this, chosen from skill, no niche locked in

Appendix — adding the Mac, Day 31+

Is the Mac better? No. For this plan the honest gap is close to zero.

Windows + WSL2Mac
Python, Node, Docker, GitIdenticalIdentical
Tutorial commands work verbatimYes, inside WSLYes
Running local models (Ollama) / heavy toolingBetter with an NVIDIA GPUGood on Apple Silicon (unified memory)
Battery and portabilityDepends on the laptopBetter
One filesystem, no /mnt/c boundarySmall annoyanceCleaner

The Mac's only real edges are portability and the absence of a Windows/Linux filesystem boundary. Neither is worth 90 days of friction. Stay on the PC.

Using both — PC at home, Mac when portable

Doable, and normal professional practice, but not before Day 31. In the first month two environments double the config breakage you have to debug, and you can't yet tell a real bug from a setup problem — that confusion costs beginners entire days. From Day 31 setting the Mac up becomes a useful 45-minute exercise. Do it on a rest day.

# Homebrew — the package manager
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"

# Core tools
brew install python@3.13 git node uv ripgrep semgrep

# Claude Code
npm install -g @anthropic-ai/claude-code

# Same Git identity as the PC
git config --global user.name "Your Name"
git config --global user.email "you@email.com"
git config --global init.defaultBranch main

# Clone your work — same path as the PC, on purpose
mkdir -p ~/dev && cd ~/dev && git clone https://github.com/YOURNAME/90-day.git

Then install Cursor and Docker Desktop from their websites. Paths match on purpose — ~/dev/ on both machines, so no command in this plan ever needs changing.

Rules for running two machines

RuleWhy
Push before you close. Pull before you start. Every time.The only real risk. A missed push means a merge conflict you can't yet resolve.
One machine per project, per dayNever edit the same repo on both machines in one day
API keys are set separately on each machineThey live in ~/.bashrc on WSL and ~/.zshrc on the Mac. They do not sync.
Same versions on bothCheck python3 --version and node --version. Mismatched versions produce bugs that exist on one machine only — the worst kind to debug as a beginner.
Never switch machines mid-taskFinish the thing, commit, push, then switch

Three Mac habits that will trip you up

  • Cmd, not Ctrl, for copy/paste/save — but inside the terminal Ctrl+C still means “kill the running process” on both systems.
  • No apt. Use brew install X wherever this plan says sudo apt install X.
  • Finder hides your dev folders. Cmd+Shift+. shows hidden files; Cmd+Shift+H jumps to your home folder.
